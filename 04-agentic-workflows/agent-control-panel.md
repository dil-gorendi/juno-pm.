## What Juno Is Doing

Each weekday before the first meeting (RADAR_TIME, default 08:00), Juno posts one Risk radar card in a private PM Slack channel. The card shows up to 3 open support threads with the highest risk, with their signals and 1 next step for each. Level 2, semi-autonomous, in Phase 3: a scheduler starts the run, and Juno can only read and draft. In Phases 1 and 2, the PM clicks Run radar (level 1). Level 1 is not enough for daily use, because a run that needs a click does not occur when the PM is away. Pattern: ReAct as a fixed prompt chain. The model has no tools, so code does Act and Observe. Anthropic calls this a workflow. Failure mode to watch: silent failure. Structured Tool Outputs, the read checks, and the monitor stop it.

## Four Levers

**Stop Conditions** (Loop):

Done: today's card is in RADAR_CHANNEL, and the run log has its Slack message ID. Limits for each run: 4 model calls and 300 seconds. The SDK retries a timeout or a retryable HTTP error 1 time. Each failed check V1, V2, or V3 gets 1 repair call. A model call error gets no repair. The support desk read gets 3 attempts of 30 seconds. The Slack post gets no retry. Juno stops before model call 1 for 6 causes. The first causes are no date of today, an unreachable source, or an incomplete read. The other causes are 0 open threads, more than 200 open threads, or data gaps in more than 25% of the threads. Only 1 run occurs at a time.

**Structured Tool Outputs** (Tools):

Each of the 8 harness functions returns 1 JSON envelope: verb, run_id, ok, count, error_class, and data. Code reads ok, never free text. The thread read also returns pages_read and total_reported. If count is not equal to total_reported, ok is false, with source_incomplete. Zero open threads is a failure (empty_read), not "no risk". Each model output must match its JSON schema, with no other properties and only input IDs. The Slack post returns the message ID, or post_fail.

**Confidence Thresholds** (Verification):

These are rules, not a model score. Juno does not rank if the input has no date of today, or if more than 25% of the threads have a data gap. If the read has 0 open threads, the run stops. An Escalation needs 1 whole customer sentence, word for word, with equal spaces and the same letter case. If a message matches the keyword rule but model call 1 gives no Escalation, the card shows a Data gaps note. The last count is the newest thread count of a run that posted a card, in the run log from the last 5 weekdays. If today's count is less than half of it, the card shows "Not verified: thread count decreased from {a} to {b}". If no last count exists, the card shows "Not verified: no previous thread count". PRD decision D7 adds this rule. Before the post, Juno checks that the channel is private and that each member is in RADAR_MEMBERS.

**North Star** (Context):

You are Juno, the AI Associate PM of RocketShip. Your single goal is this: each weekday before the first meeting, show the PM up to 3 open threads with the highest risk. Give the signals and 1 next step for each thread. You show the risks. The PM makes all decisions. Use only the IDs, names, dates, and numbers in the input. This text is the first line of model call 1, model call 2, and each repair call.

## Rules of Engagement

**Agency Permission:**

Juno can read open threads, calculate signals, rank, write next steps, and post or edit the card in RADAR_CHANNEL. Each next step and each Escalation flag is a proposal. A colleague acts only after the PM decides. Juno CANNOT change a thread: no owner, status, committed date, or priority changes. Juno CANNOT reply to a customer, send a message to an owner, or create a ticket. Tiers: read auto, draft auto, write blocked, send blocked. A post to the private RADAR_CHANNEL is a draft action. Write means a change to a support thread.

**Access Control:**

In Phase 3, Juno runs under its own read-only service token (Q3), not under the access of a PM. In Phase 2, the input is a CSV export that the PM makes. READ: open support desk threads. The query asks only for the statuses in RADAR_OPEN_STATUSES. POST: RADAR_CHANNEL only, through a Slack bot with chat:write and groups:read (Q3 confirms the scopes). MODEL: a service role for JUNO_MODEL. Before each call, code removes email addresses, phone numbers, URLs, account names, and key strings. CANNOT read CRM, the reporting database, Slack messages, or the web. Only the PM, the eval reviewers, and the monitor can read the run log.

**Fallback Protocols:**

If a model output fails check V1, V2, or V3, Juno sends 1 repair call with only the failed IDs. If call 1 fails again or has an error, Juno uses the keyword rule, and the card shows "Not verified: Escalation by keyword rule". If call 2 fails again or has an error, the step shows "Next step: not verified. Open the thread." If check V4 fails, Juno posts no card and shows "Radar did not run: check V4 failed". At 300 seconds, Juno posts the card with "Not verified: time limit" if the rank is ready. If the Slack post fails, Juno does not retry. If no card exists at RADAR_TIME + 30 minutes, a separate monitor sends an email to the PM. The email gives the error class, or no_run if no run started.

**Checkpoints:**

The card goes only to the private PM channel, so the PM read is the checkpoint before any action on a thread. Phase 2 starts only after 3 conditions. The 3 live-model eval checks pass in 3 of 3 runs. The Phase 2 acceptance criteria of the PRD release gate pass. Q2 and Q4 have answers. Phase 3 starts only after 5 conditions. Escalation precision is 90% or more in 10 shadow runs. The PM finds 0 misses in 10 unflagged threads each week for 2 weeks. The human eval rubric pass bar passes on the 10 shadow runs. Q1 and Q3 have answers. The support desk API gives a total count. If the PM acts on no next step in the 10 shadow runs, the project stops. A second person approves each change to RADAR_CHANNEL, RADAR_MEMBERS, RADAR_ALERT_TO, and JUNO_MODEL.
